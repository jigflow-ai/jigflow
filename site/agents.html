Agents and Adapters

JigFlow doesn't call a model or run an agent loop. Claude Code, Codex, Cursor and the rest already do that well. An Adapter publishes the Playbook's Skills in the format your agent reads, and from then on the agent works through jfl.

Adapters

jfl publish claude-code
jfl publish agents-md

jfl init runs one for you, and you can run it again after changing the Playbook. Publishing again replaces and removes only what jfl published, and leaves your own files alone.

AdapterWhat it writes
claude-codeEach Skill as a Claude Code Skill in .claude/skills/<name>/SKILL.md, with the Guidelines and Personas it names next to it. The router Skill jigflow. Hooks in .claude/settings.json (SessionStart, Stop, SubagentStop, SessionEnd) that give each session its id and record its token usage in the Ledger. jfl's MCP server, as the jfl entry of the project's .mcp.json.
agents-mdA section of AGENTS.md explaining how to work through jfl, with Skills in .agents/skills and Personas in .agents/personas. It works with any agent that reads AGENTS.md. It writes no MCP configuration, and prints the command that registers jfl's MCP server with your agent instead.

Only usable Personas are published: the Playbook's own, your Persona Library's, and Persona Artifacts a person has activated. A Skill that names a Persona that isn't usable is told to work without it, and how to propose it.

The router Skill

jfl publish writes one Skill you never write by hand. It is built from the Bindings: it tells the agent to run jfl next, run the Skill it names on the Artifact it names, and stop when jfl says nothing is left for an agent. It lists what works on each Status of each Artifact Type, and the Skills only a person starts. For the Larapilot-style Task:

## Task

- ready: /implement, in a fresh session
- in-progress: /implement
- in-review: /review, in a fresh session
- reviewed: human work, never an agent's
- done: final

It also tells the agent how to ask you for a Confirmation, which it can never give itself. Where jfl's MCP tools include approve, your client can show you a form only you see, so the agent puts a Proposal forward with the propose tool, which asks you at once, asks again about a pending one with approve, and asks you to make a Human Transition with move. Otherwise, or when you put the form off, it tells you what waits for you and where: jfl approve, jfl reject or jfl move in your own terminal, or the Dashboard. The AGENTS.md section says the same, and every Skill of the shipped Playbooks that ends in a Proposal or a Human Transition asks the same way at the step where its work ends. An agent that runs jfl move, jfl approve or jfl reject itself is refused, and the refusal names the tool to use.

Agent sessions

jfl tells an agent from a person by JFL_SESSION. A command run with it set is an agent session's, and one run without it is a person's. The Claude Code hooks set it at the start of each session. With agents-md, AGENTS.md tells the agent to export one id of its own and keep it.

An agent session can't make a Human Transition, approve or reject a Proposal, run migrate, or create an Artifact straight into a Status with a Binding, unless that Status is an Inbox.

Focus

jfl next makes the Artifact it hands out the session's Focus, and Transitions move it. Focus lives only in the session, never in git. The Ledger uses it to charge time and tokens to the Artifact actually being worked on.

Claims and parallel sessions

An agent session's jfl move Claims the Artifact: it records the session as owner, in the file or as the tracker's assignee. jfl next prefers what the session already claims and skips what other sessions claim. jfl refuses a move on an Artifact another session claims. The Claim is released when the Artifact enters a Status with no Binding, or a final one. This is how several sessions can work one Pocock wayfinder Map at the same time without picking the same Decision Ticket.

Fresh and isolated sessions

A Binding can ask for its Skill to run in a fresh session (fresh: true), so a reviewer doesn't carry the implementer's context, or in an isolated sub-agent (isolated: true). The router Skill and jfl next say so, and the agent follows.

Autopilot

jfl next --autopilot

Autopilot is next repeated: the agent runs the Skill, asks again, and keeps going. It stops, saying why and listing what waits for a person, when:

  • nothing is left for an agent;
  • the session's last move was refused (a failing Gate, a Human Transition);
  • the Skill it handed out didn't move the Artifact on.

It never skips a checkpoint, because the checkpoints are Statuses with no Binding and Human Transitions, which autopilot can't pass.

The MCP server

jfl mcp serves the agent-safe commands over stdio as MCP tools: next, move, propose, query, show, and create into an Inbox. To a client that supports MCP elicitation, propose asks you at once to approve or reject the Proposal it puts forward, in a form the client shows only to you, and the server also offers approve, which asks the same about a Proposal still pending (see Approving in the agent's client). There, move on a Human Transition asks you, in the same kind of form, to make or refuse it. Other clients get no way to approve, reject or make a Human Transition: propose tells the agent where the Proposal waits for you, and move refuses a Human Transition. The server is always an agent session, using JFL_SESSION when set, or a fresh id for its lifetime.

jfl publish registers it for your agent, so after jfl init it is there. claude-code writes a jfl entry running jfl mcp into the project's .mcp.json, which it creates if it's missing. Publishing again replaces only that entry, and leaves your other servers and settings in the file as they are. Claude Code asks you once whether to trust the server. If you added it yourself before, with claude mcp add jfl -- jfl mcp, claude mcp remove jfl takes that copy away. A Claude Code Elicitation or ElicitationResult hook whose matcher matches the jfl server can answer the Confirmation form in your place, so jfl publish and jfl check warn about any in the project's or your settings (see Hooks that answer the form).

# .mcp.json
{
  "mcpServers": {
    "jfl": {
      "args": ["mcp"],
      "command": "jfl",
      "type": "stdio"
    }
  }
}

Codex, Cursor and the other agents that read AGENTS.md keep their MCP servers in your own per-user settings, which jfl doesn't write. So agents-md prints the one command that registers it, to run once:

To give your agent jfl's MCP tools, register them once in its own settings, which jfl doesn't write:
  codex mcp add jfl -- jfl mcp
(for Codex; in another agent, add a stdio MCP server named jfl that runs jfl mcp)

What a Skill may do

A Skill tells the agent how to do one piece of work. It reads and changes workflow state only through jfl: show and query to read, create, comment, move and propose to change. It edits code and an Artifact's body directly. If the body of an Artifact kept in a file changes outside jfl, the next move re-validates it. A changed Status or frontmatter is refused. Text an agent writes to a tracker is marked as AI-generated. A Skill that ends in a Proposal or a Human Transition ends by asking you for the Confirmation, as the shipped ones do; /playbook-author writes yours that way.

Shipped Playbooks

JigFlow ships two Playbooks, written in the same format as yours and with no special privileges, plus a Skill that builds your own. jfl init asks which to start from, with no default.

Larapilot-style

jfl init --playbook larapilot

A heavy-spec way of working, modelled on Larapilot but not tied to Laravel or PHP. It is built into jfl (extends: {builtin: larapilot}), and keeps every Artifact as a Markdown file in the repository.

Artifact TypeStatusesWhat happens
PRDinception or adopt → in-review → approved → specifiedA person creates it. /inception (new product) or /adopt (existing codebase) writes it: users, Journeys, quality targets. A person approves it. /spec then proposes its Requirements.
Requirementspecified → planned → done, or droppedHas a MoSCoW priority field and a "Done means" section. /plan proposes the Stories that implement it. A person marks it done.
Storyplanned → acceptedA slice someone can use. Once you approve the plan, /plan writes its body: acceptance criteria, then a ## Technical plan section with the context, design, conventions and testing it will be built with. /implement builds each of its Tasks the way that plan says, and /review sends back a Task that ignores it. A person accepts it.
Taskready → in-progress → in-review → reviewed → done/implement works it test-first, and the tests and lint Gates guard in-review. /review reviews it in a fresh session. A person accepting it commits it as one commit named <id>: <title>.

It ships six generic Personas (product-owner, architect, engineer, tester, reviewer, security-reviewer) and a conventions Guideline, which the one jfl init proposes from your repository replaces. The Gates are declared by name only, so their commands come from your toolchain.

Pocock

jfl init --playbook pocock

Matt Pocock's engineering skills as a Playbook. The skills already ask an agent to wait for a person at the moments that matter. Here jfl makes it wait: an agent can't approve its own breakdown, decide what happens to an issue, or commit work nobody accepted.

Artifact TypeKept inStatuses
SpecGitHub, label specready-for-agent → ticketed
TicketGitHub, label ticketready-for-agent → in-progress → in-review → ready-to-merge → done
IssueGitHub, label issueneeds-triage (an Inbox), needs-info, ready-for-agent, ready-for-human, then the Ticket's loop, or wontfix. category (bug, enhancement) is a field.
ADRfilesproposed → accepted → deprecated or superseded
MapGitHub, label wayfinder:mapopen → cleared
Decision TicketGitHub, label wayfinder:ticketopen → in-progress → resolved, or dropped, out-of-scope
Out of Scopefilesruled-out → reconsidered
  • /to-spec turns a conversation into a Spec. to-tickets breaks it into Tickets, each blocked_by the ones it waits for, as one Proposal: nothing is created until you approve it.
  • implement works a Ticket test-first once its blockers are done. code-review reviews it in a fresh session on two axes. Accepting it (jfl move <id> done) commits it.
  • /triage walks the maintainer through the Inbox, where anyone, agents included, may file an Issue. Only a person moves one on.
  • /wayfinder charts an effort too big for one session as a Map of Decision Tickets. Several sessions can work a Map at once through Claims.
  • Every other upstream skill ships too, each with the Invocation Mode upstream intends: /grill-me, /handoff, /teach and others a person starts; tdd, grilling, domain-modeling, diagnosing-bugs and others the agent reaches when relevant. setup-matt-pocock-skills is replaced by jfl init, and ask-matt by the generated router Skill.

Every gh/glab instruction in the adapted Skills uses jfl instead, so Guards, Gates, Human Transitions and the Ledger apply. The Playbook lives in its own repository (jigflow-playbook-pocock), is MIT-licensed (© 2026 Matt Pocock), and pins the upstream commit it was adapted from in an UPSTREAM file. There, scripts/sync-upstream.sh reports what upstream changed since that commit: skills added or removed, and upstream's diff for every file adapted. Keeping up is a review, not a rewrite.

Not published yet. jfl init --playbook pocock defaults to https://github.com/jigflow-ai/jigflow-playbook-pocock at v0.4.0, which doesn't exist yet. Point it at a local checkout or a mirror:

JFL_POCOCK_GIT=/path/to/jigflow-playbook-pocock JFL_POCOCK_REF=v0.4.0 jfl init --playbook pocock

It needs a GitHub repository for its Issues, and a token in GH_TOKEN. See Connectors.

Your own: playbook-author

jfl init --playbook own
wrote .jigflow/playbook.yaml, for a Playbook of your own
…
published Playbook "own" for Claude Code
Next, run the playbook-author Skill in Claude Code: it asks how you work and proposes your Playbook's Artifact Types, Statuses and Bindings for you to approve.

/playbook-author is a Skill only a person starts. It interviews you in rounds, grilling-style: numbered questions, each with a recommended answer. It asks what kinds of work you have, what state each goes through, where you want to decide yourself, and what must pass before work moves on. Then it maps the answers onto Artifact Types, Statuses, Bindings, Human Transitions, Gates, Readiness, Guards and Inboxes, and drafts the Skills those Bindings need.

It never writes the Playbook itself. Everything arrives as one Proposal, and before asking you to approve it, it shows you the output of:

jfl check --proposal P-1
jfl simulate <Type> --proposal P-1

It ships with both Playbooks, so you can also run it in a project that extends one, to change it: add a Status, replace a Skill. A Type or Skill you change overrides the base's one of the same name in your project's .jigflow/, so you keep following new releases of the rest.

Connectors

By default an Artifact is a Markdown file in .jigflow/state/, committed with the code. When the team works in a tracker instead, an Artifact Type can keep its Artifacts there, through a Connector.

A Connector is an external executable, in any language, that speaks a small JSON protocol over stdin and stdout. jfl stays the only writer. It still enforces Transitions, Gates, Readiness, Guards and Claims, and uses the Connector only to read and write the tracker. Two reference Connectors ship with jfl: jfl-connector-github and jfl-connector-linear. make build puts both in bin/.

Setting one up

The Artifact Type names its Store:

# .jigflow/types/ticket.yaml
name: Ticket
prefix: T
store: github
statuses: [needs-triage, ready-for-agent, in-progress, in-review, done]
# …

The project's playbook.yaml declares the Connector and maps Statuses and field values to the tracker's labels or states:

connectors:
  github:
    command: jfl-connector-github  # on PATH, or a path relative to the project root
    settings: {repo: acme/shop}
    marker: "_Drafted by an AI agent._"
    types:
      Ticket:
        settings: {label: ticket}       # tells Tickets apart from other issues
        statuses:
          in-progress: "status: doing"  # a label
          done: {state: closed}         # a state; {label: …, state: …} for both
        fields:
          category:
            enhancement: "kind: feature"

A Status or value you don't map becomes a label with its own name, so a tracker whose labels already match the Playbook needs no mapping. jfl init asks for the settings a shipped Playbook leaves empty and the label of each Status, or takes them as --setting github.repo=acme/shop and --label Ticket.in-progress="status: doing".

Credentials never go in the Playbook file, which is committed. A Connector reads them from the environment jfl runs in.

Linear

connectors:
  linear:
    command: jfl-connector-linear
    settings: {team: ENG}
    types:
      Ticket:
        settings: {label: ticket}
        statuses:
          ready-for-agent: {state: Todo}
          in-progress: {state: In Progress}
          done: {state: Done}

A Linear team usually keeps its workflow in workflow states, so map each Status to one. The API key comes from LINEAR_API_KEY. Ids follow the team's numbers (ENG-41 is T-41). Claims are assignees, with the session kept in a JigFlow attachment on the issue. blocked_by Links are Linear's blocking relations. Full Linear Connector docs →

Edits made in the tracker

Teammates work in the tracker too, so for its Artifacts the tracker is the source of truth. Bodies and comments are free to edit there, and a Status or Claim changed there is where jfl's next move starts from. An issue a teammate files without labels is in the Type's first initial Status. What jfl does check is that the tracker didn't change under it: after the Gates run, a move reads the item again, and refuses if its Status or Claim changed in the meantime.

jfl can't write a tracker issue's body yet. Skills that need to write one, like the Pocock Playbook's to-spec, post the text as the first comment once a person approves. jfl show <id> prints the body and the comments together.

When the tracker fails

A tracker problem (bad credentials, rate limits, the network) is reported as such, with exit status 3, so a script or an agent can tell it apart from a workflow refusal, which exits 1:

jfl move: tracker problem, not a workflow refusal: Connector "github" was rate-limited by the tracker: API rate limit exceeded. Retry in 60s.

A tracker has no transactions. A Proposal approved into a tracker creates and moves its items one request at a time, after every Gate has passed, so a failure part way leaves the items before it applied.

Writing a Connector

jfl runs the Connector once per request, in the project root. It writes one JSON request to stdin and reads one JSON response from stdout. The operations are list, get, create, status, claim and comment:

{"protocol": 1, "op": "status", "type": "Ticket", "settings": {"repo": "acme/shop"},
 "id": "41", "from": {"label": "ready-for-agent"}, "to": {"label": "status: doing"}}

A Connector knows nothing of Statuses, Transitions or sessions. jfl maps Statuses to labels and states, adds the AI-generated marker to agents' text, and names Artifacts by prefix and tracker id. The Connector only talks to the tracker. The full protocol, with every field and error kind →

JigFlow

Define your own agent workflow as a Playbook, and run it inside the coding agent you already use. The human checkpoints are enforced by the tool, not left to the agent's goodwill.

JigFlow (jigflow, alias jfl) is a single Go binary. It isn't a new agent: it sits under Claude Code, or any agent that reads AGENTS.md, and becomes the only thing allowed to write workflow state. The agent asks jfl what to work on next and asks it to record every move. jfl checks each move against the Playbook, and refuses it when the tests fail, when the work is blocked, or when the move is one only a person may make.

Why

If you work with coding agents you probably want a repeatable loop: an idea becomes a spec, the spec becomes tickets, tickets get implemented and reviewed, and a person decides what ships. Today there are two kinds of option, and both leave something out.

  • Opinionated workflow packs like Larapilot enforce exactly this loop, but it's their loop, and it's tied to one ecosystem.
  • Prompt-only skill collections like Matt Pocock's skills work in any language and are easy to change. But nothing enforces them: an agent can skip triage, approve its own plan, or merge without review. The checkpoints are conventions the agent is asked to follow.

JigFlow keeps the flexibility of the second and the enforcement of the first. You declare your own kinds of work, their lifecycles and their checks. Gates are plain commands (go test ./..., pytest, phpstan), so it works in any codebase.

The loop

The Playbook's Status machine is the workflow. Each Status of an Artifact Type is either bound to a Skill, so jfl next hands it to an agent, or it has no Binding, and then it is human work. Moves into and out of a Status can be declared Human Transitions: the agent may propose them, but only a person at an interactive terminal, or in the local Dashboard, can make them.

What you get

  • Your own Artifact Types: PRDs, Specs, Tickets, ADRs, whatever your process has, each with its Statuses, Transitions, fields and Links.
  • Enforced checks: Gates (commands that must pass), Readiness (e.g. every blocked_by is done) and Guards on Linked Artifacts.
  • Proposals: an agent's plan, like a breakdown into ten Tickets, arrives as one unit a person approves or rejects.
  • Storage where the team wants it: Markdown files in git, or GitHub Issues and Linear through Connectors.
  • Visibility: a local Dashboard, and a committed Ledger of time per Status and tokens per Artifact.
  • Two shipped Playbooks and a playbook-author Skill that builds yours by interviewing you.

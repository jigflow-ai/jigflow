Ledger

How long did this Task wait for review? How many tokens did the agent spend on it? The Ledger answers from records jfl keeps itself, committed with the code, and never from numbers the agent reports.

jfl ledger
Time per Artifact:
  PRD-1 PRD "Todo app"
    inception  0s
    in-review  0s so far
Time per Status:
  PRD
    inception  0s over 1 Artifact
    in-review  0s over 1 Artifact, 1 there now
Agent time unattributed: 0s

From the Getting started project, a moment after moving PRD-1 to in-review.

What it records

  • Time per Status: every create, Transition, approved Proposal and migration adds an entry, so jfl ledger can sum how long each Artifact spent in each Status, and how long it has been in the current one.
  • Agent session time: every change of a session's Focus adds an entry. The time between two changes is charged to the Artifact in Focus, or to unattributed when nothing was.
  • Confirmations: every Status change a Human Transition or an approved Proposal makes, and every change an approved Proposal makes to the Playbook, records the channel of the person's Confirmation behind it. See below.
  • Tokens, where the agent's own records expose them. With Claude Code, the hooks jfl publish claude-code installs read Claude Code's session transcripts after each turn, each sub-agent and at the end of the session. They charge each message's tokens to the Artifact that was in Focus when the message was written.

Agents without such records, like those reading AGENTS.md, get time only. jfl ledger shows tokens once some have been recorded.

Where each Confirmation came from

A Human Transition, or a Proposal, needs a person's Confirmation, given somewhere the agent can't answer for them. The Ledger entry of every Status change it makes says where, in a via field:

  • terminal: the person answered y to jfl move or jfl approve at an interactive terminal;
  • dashboard: the person clicked in the Dashboard;
  • agent: the person answered a form the agent's client showed only to them, through jfl mcp.

A hook in the agent's client that answers that form, or changes the answer, is recorded via: agent too: the Ledger can't tell it from the person. jfl check, jfl publish and the Dashboard warn about such hooks (see Hooks that answer the form).

An approved Proposal records its channel on every Status change it makes, each creation and each move. Status changes that need no Confirmation, such as an ordinary Transition, an agent's move or a migration, have no via, nor do entries written before jfl recorded channels. They still read as before.

at: 2026-09-29T06:53:34.363870877Z
artifact: T-1
type: Ticket
title: Add login page
from: ready-to-merge
to: done
via: terminal

jfl ledger lists them under Confirmations, in the order they happened, each with its time in UTC, the Artifact, the change and the channel:

Confirmations:
  2026-09-29 06:53  T-1  ready-to-merge → done  via terminal

A Human Transition confirmed in a terminal.

An approved Proposal that changes the Playbook, such as a Gate's command saved in the Dashboard, adds an entry of its own naming the Proposal, its changes to the Playbook and the channel, listed with the others:

at: 2026-09-30T09:12:05.118262541Z
proposal: P-4
playbook:
  - give Gate "tests" the command go test ./...
via: dashboard
Confirmations:
  2026-09-29 06:53  T-1  ready-to-merge → done                        via terminal
  2026-09-30 09:12  P-4  give Gate "tests" the command go test ./...  via dashboard

Where it lives

The Ledger is .jigflow/ledger/, one file per entry, named by when it was written and a random id of the process that wrote it. Entries are only ever added. Parallel sessions, on one machine or on branches merged later, never touch the same file, so git never has a conflict to report. It is committed whichever Store keeps the Artifacts.

.jigflow/ledger/
  20260928T180511.825762216Z-c77d3c60-0001.yaml
  20260928T180511.834234121Z-aee1cf68-0001.yaml
  20260928T180517.367071840Z-d53a03ba-0001.yaml

Why it doesn't ask the agent

A ledger the agent can make up is worse than none. So no command or MCP tool takes usage numbers. Times come from jfl's own clock when it writes an entry, and tokens come from Claude Code's transcripts, read by a hook that refuses to run inside an agent session. As with Human Transitions, this guards against accidents, not against an agent determined to forge its own transcripts. The reasoning is in ADRs 0007, 0014 and 0015.

The Dashboard (jfl ui) shows the same sums next to the backlog, and draws them on its Timeline: each Artifact a bar across time, split by the Statuses it passed through, with the time it waited on a person hatched and the agent session time charged to it as a band under its bar. It draws only what the Ledger records, with no forecast.

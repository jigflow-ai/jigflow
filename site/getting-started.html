Getting started

This page takes an empty repository to a working loop with the Larapilot-style Playbook, which ships inside jfl. It takes about five minutes.

Install

JigFlow is one static binary, with no language runtime. Build it from the repository:

git clone https://github.com/jigflow-ai/jigflow && cd jigflow
make build                      # bin/jigflow, the bin/jfl alias, and the two Connectors
export PATH="$PWD/bin:$PATH"

With Go installed you can use go install github.com/jigflow-ai/jigflow/cmd/jigflow@latest instead, and link jfl to jigflow yourself. The GitHub and Linear Connectors are separate executables (jfl-connector-github, jfl-connector-linear), needed only when an Artifact Type is kept in a tracker.

Set a project up

mkdir todo && cd todo && git init
printf 'module todo\n\ngo 1.22\n' > go.mod
jfl init

jfl init asks, at the terminal, whatever its flags don't say:

  1. Which Playbook. Larapilot-style, Pocock, or your own. There is no default, on purpose: you choose your way of working. Without a terminal and without --playbook, it refuses and writes nothing.
  2. Which Adapter to publish the Skills through: claude-code or agents-md.
  3. Connector settings, for Artifact Types kept in a tracker: the repository or team, and the label of each Status. The Larapilot-style Playbook keeps everything in files, so it asks nothing here.

The same thing without questions:

jfl init --playbook larapilot --adapter claude-code
wrote .jigflow/playbook.yaml, extending the Larapilot-style Playbook
detected Go (go.mod)
proposed P-1: set up the Gates and a starter Guideline for the project's toolchain (3 changes, waiting for you: read it in .jigflow/proposals/P-1.yaml, then jfl approve P-1 or jfl reject P-1, or decide in jfl ui)
  1. give Gate "tests" the command go test ./...
  2. give Gate "lint" the command go vet ./...
  3. add Guideline "conventions" (18 lines)
published Playbook "todo" for Claude Code

It detects the toolchain from the files at the root: a Makefile's test and lint targets first, then Go, Rust, Python, Node.js or PHP. Nothing it detects is applied yet. It comes as Proposal P-1, which you read and then approve or reject as a whole:

jfl approve P-1
P-1 from a person: set up the Gates and a starter Guideline for the project's toolchain
  1. give Gate "tests" the command go test ./...
  2. give Gate "lint" the command go vet ./...
  3. add Guideline "conventions" (18 lines)
Approve all 3 changes as one unit? [y/N] y
approved P-1 as one unit:
  …

Your project's Playbook is now just this. Everything else comes from the Base Playbook it extends:

# .jigflow/playbook.yaml
name: todo
extends: {builtin: larapilot}
gates:
  tests: go test ./...
  lint: go vet ./...

Running jfl init again is safe. It keeps the Playbook, publishes again through the same Adapters, and asks for or proposes only what's missing.

The first loop

Create a PRD. A person creates it in inception, for a product not built yet, or in adopt, for an existing codebase:

jfl create PRD --title "Todo app" --status inception
jfl next
created PRD-1 "Todo app" in inception
run /inception on PRD-1 "Todo app"

Open Claude Code in the project and run /inception. The Skill interviews you and writes the PRD's body, then runs jfl move PRD-1 in-review. in-review has no Binding, so there the agent is done:

jfl next
nothing for an agent to do
Skipped:
  PRD-1: "in-review" has no Binding, so it's human work

Read the PRD in .jigflow/state/PRD-1.md. Approving it is a Human Transition, so jfl asks you to confirm and refuses it to an agent session:

jfl move PRD-1 approved
PRD-1 "Todo app": "in-review" → "approved" is a Human Transition. Make it? [y/N] y
PRD-1: in-review → approved

From here the Playbook does the routing:

  • /spec proposes the PRD's Requirements, each with a MoSCoW priority. You approve the Proposal.
  • /plan proposes Stories for each Requirement, broken into Tasks.
  • /implement works a Task test-first. Moving it to in-review runs the tests and lint Gates, and a failing Gate refuses the move.
  • /review reviews it in a fresh session and sends it back, or leaves it reviewed.
  • You accept it with jfl move T-1 done, a Human Transition whose Action commits the Task as one commit.

To see the whole path an Artifact Type can take, without creating anything, use jfl simulate:

jfl simulate Task
Task: 1 path from an initial Status to a final one

1. ready → in-progress → in-review → reviewed → done
   ready: Skill /implement; Readiness: every "blocked_by" item is done
     → in-progress
   in-progress: Skill /implement
     → in-review; Gates: tests (go test ./...), lint (go vet ./...)
   in-review: Skill /review
     → reviewed
   reviewed: no Binding, human work
     → done; Human Transition; Actions: commit (git add --all && git commit --quiet --message "$JFL_ARTIFACT: $JFL_TITLE")
   done: final

Let the agent drive

You don't have to name each Skill. jfl publish generates a router Skill, jigflow, that tells the agent to run jfl next, run the Skill it names, and repeat. Ask the agent to work on its own and it runs autopilot (jfl next --autopilot). Autopilot stops, saying why, when nothing is left for an agent, when its last move was refused, or when the Skill it handed out didn't move the Artifact on. What's waiting for you shows at the top of the Dashboard:

jfl ui                          # http://127.0.0.1:7457, on this machine only

Other ways to start

  • jfl init --playbook pocock: Matt Pocock's workflow, with Specs, Tickets and Issues in GitHub Issues. Until its repository is published, point it at a local checkout: JFL_POCOCK_GIT=/path/to/jigflow-playbook-pocock jfl init --playbook pocock.
  • jfl init --playbook own: then run /playbook-author in your agent, which interviews you and proposes a Playbook.

Both are described in Shipped Playbooks.

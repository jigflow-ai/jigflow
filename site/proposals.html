Proposals and the Dashboard

A Proposal is how an agent puts forward something bigger than one move: a breakdown into ten Tickets, a new Artifact Type, a Gate's command. A person approves or rejects it as one unit, and nothing in it happens until then.

Why a unit

Suppose an agent breaks a Spec into Tickets and creates them one by one. If the breakdown is wrong you find out after the fact, with half of it already in the tracker. With a Proposal the whole breakdown waits in one file. You read it, change it if you like, and approve it. Approval applies every item or none: if one fails, the files are put back as they were. While a Proposal is pending, jfl next skips the Artifacts it touches, so autopilot doesn't redo work that's waiting for you.

The Proposal file

An agent writes it and runs jfl propose <file>. jfl gives it an id and keeps it in .jigflow/proposals/:

summary: break S-1 into tickets
items:
  - {create: Ticket, ref: table, title: Reset-token table, fields: {category: enhancement}, links: {part_of: [S-1]}}
  - {create: Ticket, title: Reset endpoint, links: {part_of: [S-1], blocked_by: [table]}}
  - {move: S-1, to: ticketed}

jfl propose lists the items and says where the Proposal waits for you:

proposed P-3: break S-1 into tickets (3 changes, waiting for a human)
  1. create Ticket "Reset-token table" (category enhancement), part_of S-1
  2. create Ticket "Reset endpoint", blocked_by table, part_of S-1
  3. move S-1 → ticketed
P-3 waits for a person to approve or reject it with jfl approve P-3 or jfl reject P-3 in a terminal, or in the Dashboard (jfl ui)

A ref names an Artifact the Proposal creates, so later items can Link to it before it has an id. Quote titles that contain :, ? or ,, as YAML requires.

Item kinds

ItemWhat approving it does
{create: <Type>, title, ref?, status?, fields?, links?}Creates an Artifact. An approved Proposal may create into a Status with a Binding, which an agent can't do directly.
{move: <id or ref>, to: <status>}Makes a Transition, Human Transitions included.
{gate: <name>, cmd: <command>}Gives a Gate the project's command, in playbook.yaml's gates:.
{gate: <name>, remove: true}Removes the command playbook.yaml gives a Gate, which then runs its Base Playbook's, if any. It is refused when the file gives that Gate none.
{guideline: <name>, text: …}Adds a Guideline. It never overwrites an existing one.
{type: <name>, text: <YAML>}Declares an Artifact Type as a whole file, replacing the project's Type of that name or overriding the Base Playbook's.
{skill: <name>, text: <SKILL.md>}Writes a Skill, the same way.

The last five change the Playbook. jfl propose refuses a Proposal whose resulting Playbook would fail jfl check, or would leave Artifacts in a Status no longer declared. On approval jfl writes the files, checks the Playbook again, and restores every file if anything fails. A Proposal can't yet declare a Connector or a Playbook Migration.

Checking one before approving it

jfl check --proposal P-3
jfl simulate Ticket --proposal P-3

Both load the Playbook as the pending Proposal would make it, in memory, and write nothing. /playbook-author shows you their output before it asks you to approve.

Approving and rejecting

jfl approve P-3        # lists every item, then asks: Approve all 3 changes as one unit? [y/N]
jfl reject P-3

An item that changes a value of the Playbook file, such as a Gate's command, is shown with the value it replaces: by jfl approve before it asks, in the form of the agent's client, by jfl show P-3 while the Proposal is pending, and on the Proposal in the Dashboard. It is the value as it is when you look, not when the Proposal was put forward, so a command you changed meanwhile is the one you see being replaced:

P-3 from agent session A: race the tests
  1. give Gate "tests" the command go test -race ./... (replacing go test -short ./...)
Approve all 1 change as one unit? [y/N]

Only a person may approve or reject: at an interactive terminal, in the Dashboard, or in a form the agent's client shows only to them. An agent session running jfl approve or jfl reject is refused, and told to ask you with the approve tool of jfl mcp where its client can show you a form, or otherwise to tell you the Proposal waits for you. A Human Transition refused to an agent's jfl move names the move tool the same way. If an item makes a Transition that the Playbook marks human: dashboard, the Proposal can only be approved in the Dashboard. The Ledger records which of the three each approval, and each Human Transition, came through.

Approving in the agent's client

If your agent's client supports MCP elicitation, the jfl mcp server asks you as soon as the agent puts a Proposal forward with its propose tool, while the context is fresh. It also offers the agent an approve tool, to ask you again about a Proposal still pending. Either way your client shows you a form that the model never sees:

P-3 from agent session A: break S-1 into 2 tickets
  1. create Ticket "Reset-token table" in ready-for-agent, part_of S-1
  2. move S-1 → ticketed
Approve all 2 changes as one unit, or reject P-3?

Decision: ( ) approve  ( ) reject

jfl writes the form from the Proposal itself, so what you approve is what will happen. You must pick one: approve applies the Proposal exactly as jfl approve at a terminal would, with its Gates, Actions, re-validated bodies and trackers, and reject drops it. Dismissing or declining the form changes nothing: the Proposal stays pending for the terminal, the Dashboard, or the agent asking again later. You can't edit items in the form; reject, and ask the agent to propose again, or edit them in the Dashboard. A Proposal that makes a human: dashboard Transition is refused without a form, with the same pointer to the Dashboard. The tool isn't offered to a client that can't show forms. See ADR 0024.

The same goes for a Human Transition. When the agent asks the move tool for one, the client shows you a form written from the Artifact:

T-1 "Add login page": "ready-to-merge" → "done" is a Human Transition. Make it, or refuse it?

Decision: ( ) make  ( ) refuse

make makes it exactly as jfl move confirmed at a terminal would, with its Gates, Actions, Guards, re-validated body, Claim and tracker, and the Ledger records it via: agent. refuse, or dismissing or declining the form, leaves the Artifact where it is, and the agent is told so. Activating or retiring a Persona works the same way. A human: dashboard Transition is refused without a form, with the pointer to the Dashboard, and a client that can't show forms gets the usual refusal.

Hooks that answer the form

A Claude Code hook can reach the form before you do. An Elicitation hook whose matcher matches the jfl server answers the form without showing it to you, and an ElicitationResult hook can change the answer you gave. Either can approve Proposals and make Human Transitions in your place, and the Ledger records them via: agent, since it can't tell them from you. A hook written for another server with a broad matcher, such as * or .*, matches jfl too. jfl check and jfl publish warn about each one in .claude/settings.json, .claude/settings.local.json or your user settings, and the Dashboard shows the same warning:

jfl: warning: .claude/settings.json has an Elicitation hook whose matcher "*" matches jfl's MCP server (runs auto-answer.sh): it can answer the Confirmation form without showing it to you, and so approve Proposals and make Human Transitions in your place; the Ledger records them as Confirmations given in the agent's client

It is only a warning, and the command still succeeds: a hook you added on purpose keeps working. Remove the hook, or narrow its matcher to the servers it's for, if you didn't mean it.

The Dashboard

jfl ui
Dashboard at http://127.0.0.1:7457/?key=P3OOB3YVWLWHN5RDIL6UXQXENL
Open this link in your browser to approve Proposals, make Human Transitions, comment and change the Playbook file there; it is yours alone, until jfl ui stops.

jfl ui serves a local web view until you interrupt it. It shows:

  • your human queue and pending Proposals, first;
  • the Artifacts of each Type with their Status, Claim, Links and who they're waiting on;
  • a page for each Artifact, which every id links to: its body rendered as Markdown, its fields, Status, Claim and who it waits on, the Artifacts it links to and those linking to it (a Story's Tasks, with how many are done), its history from the Ledger, its Human Transitions, the pending Proposals that move it or create something linked to it, in a git repository the commits that name it, and a form to comment on it;
  • the Playbook: its Artifact Types, Bindings, Skills with their Invocation Mode and the Statuses they are bound to, Guidelines, Personas, each shipped, proposed, active or retired, Gates, each with its command or, for a Gate declared by name only, whether the project's Playbook file gives it one yet, and the pending Proposal changing it too, if one does, the Mockup folder, when there is one, and every Adapter, marked when the Skills are published through it. Each part says where it comes from: jfl itself, a builtin or other Base Playbook, the project, or the project overriding its Base Playbook's. Each Skill, Guideline and Persona opens to its file rendered as Markdown. With the link jfl ui printed, each Gate has a field holding its command: see Changing the Playbook file; and each Adapter a button to publish for its agent, or stop: see Adapters. The rest of the Playbook changes through Proposals;
  • the Timeline: how the work actually went, drawn from the Ledger only, with no forecast. Each Artifact is a bar across time, split and coloured by the Statuses it passed through; one still in a Status is drawn up to now. Time in a Status with no Binding, waiting on a person, is hatched, and the agent session time charged to it is a thin band under its bar. Each bar links to its Artifact's page and gives its Status and dates on hover. Rows nest under the target of the Artifact's first declared Link to a different Artifact Type, a Task under its Story, a Story under its Requirement; a Link to the same Type, such as blocked_by, doesn't nest. On a backlog kept in a tracker, the page says that moves made in the tracker itself aren't in the Ledger, and so aren't drawn;
  • the Design page, when the Playbook declares a Mockup folder: every Mockup in it, HTML pages and pictures, previewed and grouped by the subfolder named after the Artifact it belongs to, each group linked to that Artifact's page; subfolders named after no Artifact, and files in none, are listed apart. An Artifact's page shows, under Mockups, a preview of each Mockup its body links to, and says which of them the folder doesn't have. With no Mockup folder there is no Design page;
  • the Git page, when the project is in a git repository: the current branch's commits, newest first, fifty to a page. A commit whose subject starts with a known Artifact's id and a colon, as the commit Action names it when a person accepts a Task (T-1: Reset-token table), links to that Artifact's page, and each Artifact's page lists, under Commits, the commits whose subject starts with its id. Outside a git repository, neither is shown;
  • the Ledger, summed;
  • each Artifact Type's Status machine, drawn;
  • a warning about hooks that can answer the form for you, when there are any.

In the browser you can approve or reject Proposals, editing a proposed creation's title, starting Status and Links first, and make Human Transitions. It is the preferred place for these decisions, because you see the context next to the decision.

You can also comment on an Artifact from its page. The Dashboard runs jfl comment for you, as you, so the comment is signed as a person's, not an agent's: on an Artifact kept in a file it is appended to the body, and on one kept in a tracker it is added there as a comment. Agents read it through jfl show like any other. The page then shows your comment, or why jfl comment refused it, with what you wrote kept in the form. Commenting needs the link jfl ui printed, like every decision, and a Dashboard an agent session started offers no comment form. It is the only way the Dashboard adds to a body.

You can change a Gate's command from the Playbook page, instead of editing .jigflow/playbook.yaml by hand. Each Gate has a field holding its command, next to where it comes from: the project's Playbook file, a Base Playbook, or none yet. Saving the field makes a Proposal of yours, {gate: <name>, cmd: <command>}, and approves it in the same click, exactly as jfl propose and jfl approve would: the command is written into the Playbook file, which keeps the rest of what it says, its comments included, the Playbook is checked again and every file put back if it fails, and the Ledger records the Confirmation via: dashboard. The page then shows what jfl said, or why it refused. A command the project gives over its Base Playbook's has a Back to the Base's button, which removes the project's command the same way, with {gate: <name>, remove: true}. Nothing is committed: the change waits in your working tree, like any other. A Gate whose command a pending Proposal also changes says so, naming and linking that Proposal. Saving the field still goes through, and leaves that Proposal pending: approving it later shows the command it replaces, yours by then (see above). Without the link, the Playbook page offers no forms. See ADR 0030.

The Playbook page also lists every Adapter, with the coding agent it publishes for, marked published when the Playbook's Skills are published through it. Which Adapters those are is no setting: jfl reads it from .jigflow/published.yaml, and jfl init publishes through them again. With the link, Publish for an agent runs jfl publish <adapter> for you, and Stop publishing for one runs jfl publish --remove <adapter>, which deletes only what that Adapter published. The page then shows what jfl said. Neither is a Proposal: they change no workflow state, and an agent may run jfl publish itself. Without the link, the list offers no buttons.

Keep it open while an agent works: every page updates itself when the project changes. Within a few seconds of jfl writing a change, whoever ran it (an agent's jfl move, a new Proposal, a Ledger entry, an approved change to the Playbook), or of a commit on the current branch, the page reloads and keeps your place on it. If you have started editing a Proposal, changing a proposed creation's title, starting Status or Links, or writing a comment, the page doesn't reload: a bar at the top says the project changed, with a Reload link, and your edits stay. Approve when you are ready, and your edits are applied; if the Proposal was approved or rejected meanwhile, in a terminal or by another page, the approval is refused and the page says why. Nothing reloads only because time passed, so the Ledger page says as of when its times are, and the Timeline says when it is drawn up to. If your backlog is kept in a tracker, GitHub Issues or Linear, an edit made in the tracker itself (an item's labels or Status, a new item) shows within 30 seconds; changes made through jfl still show at once. Each page asks jfl ui every 2 seconds, while its tab is visible, whether the project changed since what it shows, and once as soon as you come back to a hidden tab; a hidden tab doesn't ask, and no page holds a connection open, so you can keep as many tabs open as you like. When asked, jfl ui looks over .jigflow/, the Mockup folder and the current branch at most once a second, and asks the tracker at most every 30 seconds, however many pages ask and not at all while none does, so it costs little against the tracker's rate limit; a tracker that can't be reached changes nothing on the page until it can. The answer carries only whether something changed, never what, so a Dashboard an agent session started updates too. The pages use a few lines of inline JavaScript for this, with no build step; with JavaScript off, every page and every decision works as before, and you reload by hand. See ADR 0025 and ADR 0029.

The Dashboard listens only on a loopback address (127.0.0.1 unless --addr names another). Decisions need the link jfl ui prints, which carries a random key made each time it starts. An agent that finds the port with curl can look, but can't decide. A Dashboard started by an agent session is read-only. It never edits an Artifact's body, except to add your comment through jfl comment, and shows any HTML written in one as text, so a body can't put a script on a page that carries your decisions. Mockups do run their own scripts, styles and images, but the Dashboard serves them only from the Mockup folder, never anything outside it, through .. or a symbolic link, and each with Content-Security-Policy: sandbox allow-scripts: a Mockup runs in an origin of its own, and can't read the Dashboard, its storage or its key, nor decide anything for you. See ADRs 0016 and 0017 and 0027.

What Human Transitions protect against

Human Transitions and approvals guard against accidents: an agent that moves on too eagerly, a Skill that forgets to wait. An agent can run any shell command, so they can't stop a determined one. The CLI asks for confirmation at an interactive terminal, and the MCP server asks for it only in a form the agent's client shows to you, never to the model. The Dashboard is the stronger channel, since an agent in a terminal can't click in your browser, and a Playbook can require it for a Transition with human: dashboard (ADR 0003).

What gets around it

An agent that sets out to act as you can. These are the ways jfl knows of:

  • Posing as you. jfl tells an agent from you only by JFL_SESSION, which the Adapter's hooks, or the agent itself, set. An agent that runs jfl without it, in a pseudo-terminal it makes, looks like you typing y.
  • A hook that answers the form. An Elicitation or ElicitationResult hook can answer the form, or change your answer, without you seeing it. jfl warns about the ones it finds (Hooks that answer the form).
  • A Dashboard of its own. An agent that starts jfl ui without JFL_SESSION, or reads the link from your terminal or the key from your browser's cookies, can decide in the Dashboard (ADR 0017).
  • Before the restart after setting up from the agent. Until Claude Code restarts, no hook sets JFL_SESSION: /jigflow-init tells the agent to set it, and nothing makes it (ADR 0026).

What jfl does refuse: a Status or frontmatter changed by editing the Artifact's file, which the next jfl move refuses; jfl approve, jfl reject and a Human Transition in an agent session; and the MCP server making one without the form. To check afterwards, jfl ledger shows the channel of every Confirmation, terminal, dashboard or agent (Where each Confirmation came from): one you don't remember giving is worth a look. To make it a boundary rather than a guardrail, run the agent where it can't act as you, such as a container that can't write the project's .jigflow/; jfl doesn't do that for you.

Fewer approvals, on purpose

If the Playbook asks you more often than you want, change the Playbook rather than working around it: drop human from a Transition to make it an ordinary one an agent may make (Transitions), or make a Status an inbox, which agents may create into directly (Artifact Types). Either is a change to the Playbook, so it comes as a Proposal you approve once, from /playbook-author or an agent. A Proposal itself has no switch to skip approving: the quickest is the form propose shows the moment it is put forward.

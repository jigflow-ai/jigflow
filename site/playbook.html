Playbook reference

A Playbook is a directory of plain files: YAML for the workflow, Markdown for what agents read. This page lists every file and every key. The examples come from the Larapilot-style and Pocock Playbooks, which both pass jfl check.

You rarely write one from scratch. Usually a project extends a shipped Playbook and overrides a few parts by name, or asks /playbook-author to propose the changes. Either way, agents never edit these files. A change to the Playbook reaches the project as a Proposal a person approves, or as a person's own edit.

Layout

.jigflow/
  playbook.yaml            # name, extends, gates, connectors, mockups
  types/*.yaml             # one Artifact Type per file, declared in file-name order
  skills/<name>/SKILL.md   # Skills
  guidelines/<name>.md     # Guidelines
  personas/<name>.md       # Personas
  migrations/*.yaml        # Playbook Migrations (the project's only)
  state/                   # Artifacts kept in files: written by jfl, never by hand
  proposals/               # Proposals
  ledger/                  # the Ledger: one committed file per entry
  playbook.lock            # the commit a git Base Playbook's ref resolved to

A Playbook shipped on its own, like the Pocock one, has the same layout at the root of its repository, without the state directories.

playbook.yaml

name: shop
extends: {git: https://github.com/jigflow-ai/jigflow-playbook-pocock, ref: v0.4.0}
gates:
  tests: go test ./...
  lint: go vet ./...
mockups: design/screens
connectors:
  github:
    command: jfl-connector-github
    settings: {repo: acme/shop}
    types:
      Ticket:
        settings: {label: ticket}
        statuses:
          in-progress: "status: doing"   # a label
          done: {state: closed}          # a state
KeyWhat it is
nameThe Playbook's name, shown by publish and the router Skill.
extendsThe single Base Playbook.
gatesThe project's command for each Gate named here, wherever the Playbook declares it. It overrides a declared command. This is how a shipped Playbook declares a Gate by name only and leaves the command to you.
connectorsThe Connectors that Stores name, with their settings and how Statuses and fields map to the tracker. See Connectors.
mockupsThe one folder for Mockups, the pages and pictures that show what a piece of work should look like, relative to the project root and inside it. Each goes in a subfolder named after the Artifact it belongs to, and a body links it by its path from the project root, such as .jigflow/mockups/REQ-1/checkout.html. It overrides the Base Playbook's: the Larapilot-style Playbook sets .jigflow/mockups, and a Playbook that declares none has no Mockups. jfl check says where it is. The Dashboard serves only the files in it, sandboxed, and shows them on its Design page and on the pages of the Artifacts linking them.

Base Playbooks: extends

A Playbook extends at most one Base Playbook, named in one of three ways:

extends: {builtin: larapilot}                                # built into jfl
extends: {path: ../playbooks/ours}                           # a directory, relative to the project root
extends: {git: https://github.com/acme/playbook, ref: v2.1.0} # a git repository, pinned to a ref

The extending Playbook's parts override the base's parts by name: an Artifact Type, Skill, Guideline, Persona, Connector or Gate command of the same name replaces the base's one, a Mockup folder replaces the base's, and everything else is kept. A replaced Artifact Type keeps the base's place in the declaration order, and new ones come after the base's. The Dashboard's Playbook page (jfl ui) lists every part and says where it comes from: the Base Playbook, the project, or the project overriding the base's. For a git base, jfl records in .jigflow/playbook.lock the commit the ref resolved to, and keeps using it until you change the ref.

Artifact Types: types/*.yaml

This is the Larapilot-style Task, complete:

name: Task
prefix: T                       # ids are T-1, T-2, …
links:
  part_of: Story
  blocked_by: Task
statuses: [ready, in-progress, in-review, reviewed, done]
initial: [ready]
final: [done]
bindings:
  ready: {skill: implement, fresh: true}
  in-progress: implement
  in-review: {skill: review, fresh: true}
readiness:
  ready:
    - {kind: linked-all-in, link: blocked_by, statuses: [done]}
transitions:
  - {from: ready, to: in-progress}
  - from: in-progress
    to: in-review
    gates:
      - {name: tests}
      - {name: lint}
  - {from: in-review, to: in-progress}
  - {from: in-review, to: reviewed}
  - {from: reviewed, to: in-progress, human: true}
  - from: reviewed
    to: done
    human: true
    actions:
      - {name: commit, cmd: 'git add --all && git commit --quiet --message "$JFL_ARTIFACT: $JFL_TITLE"'}
KeyWhat it is
name, prefixThe Type's name, used in commands (jfl create Task), and the prefix of its Artifacts' ids.
storefiles (the default) keeps Artifacts as Markdown in .jigflow/state/. Any other value names a Connector.
fieldsEach field with the values it may take, e.g. priority: [must, should, could, wont]. They're set at creation (--field priority=must, or in a Proposal).
statusesEvery Status, in order.
initial, finalWhere Artifacts may be created, and where they end. Entering a final Status releases a Claim.
inboxStatuses anyone, agents included, may create into directly. jfl check refuses an Inbox from which a Skill that changes code or Artifacts is reachable without passing a Human Transition.
linksNamed, typed Links to Artifacts of other Types (or the same one). Their order counts: the Dashboard's Timeline nests an Artifact under the target of its first declared Link to a different Type, so declare the one to its parent first, as part_of: Story above.
bindingsFor each Status an agent works on, the Skill that does it. A Status with no Binding is human work.
readinessPer Status, the conditions that must hold before agent work may start there.
transitionsEvery allowed move. Anything not listed is refused.

Bindings

bindings:
  in-progress: implement                              # just the Skill
  in-review: {skill: review, fresh: true}             # in a fresh session
  ready: {skill: implement, isolated: true}           # in an isolated sub-agent

The set of Bindings is the Playbook's topology: jfl next hands out only bound Statuses, and the router Skill lists them. A Status keeps a Claim only while it has a Binding.

Transitions

KeyWhat it is
from, toThe two Statuses.
humantrue makes it a Human Transition, confirmed at an interactive terminal, in the Dashboard, or in a form the agent's client shows only to the person, and refused to agent sessions. dashboard requires the Dashboard.
gatesCommands that must succeed before the move. A failing Gate refuses the move and prints its output.
actionsCommands run after the move succeeds (commit, open a branch, notify).
guardsConditions on Linked Artifacts, checked at the moment of the move.

A Gate or Action is {name, cmd}. A Gate may give only a name, with the command coming from playbook.yaml's gates:. Until it has one, the Playbook still loads, but a move through that Gate is refused with a message saying where to set it. Both run through the shell in the project root with no stdin, and see JFL_ARTIFACT (the id), JFL_TITLE, JFL_FROM and JFL_TO in their environment.

Readiness and Guards

Both take a list of conditions, of two kinds:

- {kind: linked-all-in, link: blocked_by, statuses: [done]}   # every Artifact this Link points to is in one of these Statuses
- {kind: has-incoming, link: part_of, min: 1}                 # at least min Artifacts point here through this Link

Readiness is declared per Status and holds agent work back: jfl next skips an Artifact that isn't ready and says why. A Guard is declared on a Transition and is checked only when the move is made. The Larapilot PRD, for example, can't reach specified until at least one Requirement is part_of it.

Skills: skills/<name>/SKILL.md

---
description: Implement the Task in Focus as one change that passes the project's tests and lint, then hand it to review.
changes: true
invocation: bound
guidelines: [conventions]
personas:
  - name: engineer
    fallback: "Makes the smallest change that does the job well, in the style of the code around it…"
---
Implement the Task in Focus.

1. If it is in ready, run `jfl move <id> in-progress`. …
KeyWhat it is
descriptionWhen to use it. Adapters publish it for the agent.
changesRequired: true if the Skill changes code or Artifacts. jfl check uses it to validate Inboxes.
invocationRequired Invocation Mode: user (a person starts it), agent (the agent may use it whenever relevant) or bound (only through a Binding).
guidelinesGuidelines published next to the Skill, for it to load when needed.
personasPersonas to adopt. The fallback describes one that isn't usable yet, so the agent can work without it and propose it.

A Skill never writes workflow state itself. It reads and changes Artifacts through jfl (show, query, create, comment, move, propose), so every check applies. Don't write a router Skill by hand: jfl publish generates it from the Bindings.

Guidelines and Personas

A Guideline (guidelines/<name>.md) is a rule file Skills name and load only when needed. It is the home of language and codebase conventions. jfl init proposes a starter conventions Guideline from what it finds in the repository.

A Persona (personas/<name>.md) is a named point of view a Skill asks the agent to adopt. Personas the Playbook ships, and those of your Persona Library (~/.config/jigflow/personas), are usable as they are. One an agent proposes is an Artifact of the built-in Persona Type, and becomes usable only when a person moves it to active. A project Persona overrides a Library one of the same name.

Playbook Migrations: migrations/*.yaml

When a Playbook, or its Base Playbook, stops declaring a Status that Artifacts are in, every command except check refuses to run until they're moved. A Migration maps the old Statuses to new ones, per Artifact Type:

# .jigflow/migrations/doing.yaml
Ticket:
  in-progress: doing

jfl migrate applies them, all or none, and only a person may run it. Only the project declares Migrations, since its Artifacts are what they move.

Checking a Playbook

jfl check                    # every problem, in the Playbook merged over its base
jfl simulate Task            # each path from an initial Status to a final one
jfl simulate Task --source   # the file declaring it first, a built-in base's too

simulate walks a pretend Artifact through the Playbook, listing the Skill, Readiness, Guards, Gates, Actions and Human Transitions along each path. It writes no state and runs nothing. Both take --proposal P-n to check the Playbook as a pending Proposal would make it, before anyone approves it.
